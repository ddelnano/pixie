## Goal

Integrate Object Introspection (OI) into Pixie so that OI's memory profiling data flows through Pixie's data pipeline and is queryable via pxl scripts with native visualizations (histogram and flame graph).

## Background

### Object Introspection

Object Introspection (OI) is a memory profiling tool for C++ objects. It dynamically instruments a running process to capture the precise memory occupancy of entire object hierarchies — including all containers and dynamic allocations — with no code modification or recompilation. See @/home/ddelnano/code/object-introspection/README.md .

OI outputs nested JSON describing each object's static size, dynamic size, padding savings, and recursively its members and container elements. See @/home/ddelnano/code/object-introspection/website/docs/addrbook-this.md for a concrete example of this output structure.

### Why This Matters

OI enables two categories of memory optimization:

1. **Container sizing** — Profiling reveals the actual element count distribution for dynamically-sized containers (e.g., `std::vector`, `folly::small_vector`). If a `small_vector<T, 10>` is mostly used with 1–4 elements, it can be resized to dramatically reduce memory footprint. See @/home/ddelnano/code/pixie-worktree/oi-applied-example1.png .

2. **Padding and layout issues** — A flame graph of an object's nested memory footprint exposes padding waste and alignment problems (e.g., bad struct packing from code generation like Thrift/Protobuf annotations). See @/home/ddelnano/code/pixie-worktree/oi-applied-example2.png .

- **Test**: `src/stirling/source_connectors/dynamic_tracer/stirling_dt_bpf_test.cc` — `DynamicTraceAPITest.ObjectProfileAPI` launches an AddrBook binary (based on OI's AddrBook example at @/home/ddelnano/code/object-introspection/examples/web/AddrBook ), deploys a tracepoint with `OI_ENTRY` type, and runs Stirling's data collector.
- **Connector**: `src/stirling/source_connectors/dynamic_object/dynamic_object_connector.{h,cc}` — `DynamicObjectTraceConnector` manages a subprocess lifecycle (start, monitor, relaunch) against a target PID with TTL and count semantics. Currently it reads the target process's stdout via `cat /proc/<pid>/fd/1` as a placeholder for the real OI binary.
- **Table**: A minimal `object_trace` table with only a `time` column — no actual OI data is stored.

## Gaps

1. **Real OI binary integration** — The connector currently reads target stdout instead of invoking an actual OI binary (`oid`). It needs to invoke `oid` with the correct probe specification (e.g., `entry:_ZN11AddressBook12DumpContactsEv:this`) against the target PID and parse its JSON output.

2. **DataTable schemas** — The current `object_trace` table has only a `time` column. We need two statically-defined tables (see `src/stirling/source_connectors/socket_tracer/http_table.h` for an example) with schemas designed for Pixie's existing visualization widgets. See "Design: Flatten at Ingestion" below for rationale.

3. **Data persistence** — `TransferDataImpl` must parse OI's JSON output, walk the nested tree in C++, and emit flat rows into both DataTables.

4. **PXL scripts for visualization** — Two pxl scripts are needed, one per table/visualization type. See Phase 3 below.

## Design: Flatten at Ingestion

pxl (Pixie's query language) supports dataframe operations (filter, groupby, agg, merge) but has no recursion or arbitrary-depth iteration. Functions like `px.pluck()` and `px.pluck_float64()` extract known keys from JSON but cannot walk an unknown/variable-depth tree. This means **OI's arbitrarily nested JSON cannot be traversed in pxl**.

The solution is to flatten the OI hierarchy in C++ at ingestion time, producing pre-flattened rows that pxl can consume directly. This follows the same pattern used by Pixie's CPU profiler: the `stack_traces.beta` table (see `src/stirling/source_connectors/perf_profiler/stack_traces_table.h`) stores stack traces as semicolon-delimited folded strings (e.g., `"main;func1;func2"`), which the `StackTraceFlameGraph` vis widget renders directly.

The connector's C++ code will use rapidjson (already in the codebase) to recursively walk OI's JSON output and emit flat rows into two separate tables:

### Table 1: `object_memory_traces` (flame graph)

Each row represents one path from the object root to a member/leaf, with memory size as the count. This directly reuses the `StackTraceFlameGraph` visualization widget.

| Column | Type | Example | Description |
|---|---|---|---|
| `time_` | TIME64NS | | Timestamp of the OI capture |
| `upid` | UINT128 | | Target process identifier |
| `stack_trace` | STRING | `"AddressBook;Owner;[string data]"` | Semicolon-delimited path from root to member, in folded format |
| `count` | INT64 | `96` | Memory size in bytes (staticSize + dynamicSize) at this node |
| `padding_savings` | INT64 | `4` | Potential padding savings in bytes at this node |

The `stack_trace` column format mirrors CPU profiling folded stacks. The connector walks OI's JSON tree and for each node emits a row with the full ancestor path. For example, given OI output for an `AddressBook` with member `Entries` containing `Contact[0]` with member `firstName`, the connector emits:

```
stack_trace="AddressBook"                                    count=23249
stack_trace="AddressBook;rev"                                count=4
stack_trace="AddressBook;Owner"                              count=56
stack_trace="AddressBook;Entries"                             count=23185
stack_trace="AddressBook;Entries;Contact[0]"                  count=432
stack_trace="AddressBook;Entries;Contact[0];firstName"        count=96
...
```

### Table 2: `object_container_stats` (histogram)

Each row represents one container observation — its path, type, and element count. This enables histogram visualization of container size distributions over time.

| Column | Type | Example | Description |
|---|---|---|---|
| `time_` | TIME64NS | | Timestamp of the OI capture |
| `upid` | UINT128 | | Target process identifier |
| `container_path` | STRING | `"AddressBook.Entries"` | Dot-delimited path to the container within the object |
| `container_type` | STRING | `"std::vector<Contact>"` | C++ type of the container |
| `element_count` | INT64 | `47` | Number of elements in the container at capture time |
| `total_size` | INT64 | `23185` | Total memory (static + dynamic) consumed by this container |

The histogram pxl script bins on `element_count` with `px.bin()` and aggregates with `groupby`, exactly like the MySQL latency histogram in @/home/ddelnano/code/pixie-worktree/src/pxl_scripts/px/mysql_stats .

## Implementation Plan

### Phase 1: DataTable Schemas

Define two static table schemas in `src/stirling/source_connectors/dynamic_object/`:

1. **`object_memory_traces_table.h`** — The flame graph table with `time_`, `upid`, `stack_trace`, `count`, and `padding_savings` columns. Follows the pattern of `src/stirling/source_connectors/perf_profiler/stack_traces_table.h`.

2. **`object_container_stats_table.h`** — The histogram table with `time_`, `upid`, `container_path`, `container_type`, `element_count`, and `total_size` columns.

### Phase 2: OI Binary Integration and JSON Flattening

Update `DynamicObjectTraceConnector`:
- Replace the `cat /proc/<pid>/fd/1` subprocess with an invocation of the `oid` binary.
- Construct the probe specification from the tracepoint deployment proto's symbol and targets (e.g., `entry:<mangled_symbol>:this`).
- Parse the resulting JSON output file (`oid_out.json`) using rapidjson.
- Recursively walk the JSON tree to emit rows:
  - For each node: emit a row into `object_memory_traces` with the semicolon-delimited ancestor path as `stack_trace` and the node's memory size as `count`.
  - For each container node (identified by having a `length` or element array in OI output): emit a row into `object_container_stats` with the element count and total size.

### Phase 3: PXL Scripts

Create two pxl script directories under `src/pxl_scripts/`:

1. **`px/object_memory_flamegraph/`** — Queries the `object_memory_traces` table. The `stack_trace` column is already in folded format, so this script follows the same pattern as @/home/ddelnano/code/pixie-worktree/src/pxl_scripts/px/perf_flamegraph (groupby, sum counts, compute percentages). The `vis.json` uses `@type: types.px.dev/px.vispb.StackTraceFlameGraph` with `stacktraceColumn: "stack_trace"` and `countColumn: "count"`.

2. **`px/object_container_histogram/`** — Queries the `object_container_stats` table, filters by `container_path`, bins on `element_count` using `px.bin()`, and aggregates with `groupby('element_count_bin').agg(count=('time_', px.count))`. Follows the histogram pattern from @/home/ddelnano/code/pixie-worktree/src/pxl_scripts/px/mysql_stats .

### Phase 4: End-to-End Test

Update `DynamicTraceAPITest.ObjectProfileAPI` to:
- Assume `oid` is accessible to the test binary.
- Verify that OI data flows into both DataTables with expected columns populated.
- For `object_memory_traces`: assert that rows exist with `stack_trace` paths like `"AddressBook"`, `"AddressBook;Entries"`, etc., and that `count` values are > 0.
- For `object_container_stats`: assert that a row exists for `container_path="AddressBook.Entries"` with `element_count` > 0.
- Validate the AddrBook example produces correct hierarchy data.
